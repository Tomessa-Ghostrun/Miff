# Miff - application iOS

SwiftUI, iOS 16 minimum, iPhone seulement, identifiant `com.tomessa.miff`. Contenu actuel : le **socle technique** (ticket INIT-4, miroir d'INIT-2 Android) et la **parité Android** de l'authentification et de l'onboarding : **AUTH-3** (inscription et connexion par e-mail, Google et Apple), **AUTH-4** (mot de passe oublié), **ONB-5** (icône, carrousel de bienvenue, écran de lancement animé) et **ONB-6** (profil : prénom, nom, photo, numéro de téléphone obligatoire, routage de la session). Mêmes règles métier, mêmes textes et mêmes événements qu'Android. S'y ajoute **MIFF-3** (miroir d'Android MIFF-1) : **créer une Miff, la rejoindre par son code, l'écran de la Miff, « Partager mon statut », l'accès perdu** (voir « Miffs » plus bas). S'y ajoute **LOC-3** (miroir d'Android LOC-1 : les **lieux de confiance**, voir « Lieux de confiance » plus bas). S'y ajoute **LOC-4a** (autorisations et consentement version 3) puis **LOC-4b** (miroir d'Android LOC-2b : le **suivi des lieux**, les arrivées et les départs, le statut et la dernière position, voir « Suivi des lieux » plus bas). S'y ajoute **MIFF-4** (miroir d'Android MIFF-2) : **retirer un proche, quitter une Miff, la supprimer, créer un nouveau code, « Prévenir mes proches »** (voir « Retirer, quitter, supprimer » plus bas). Le Feed (FEED-5 à FEED-7, voir « Le Feed » plus bas) remplace l'accueil provisoire dans la coquille d'ONB-7. (Texte d'origine, devenu historique : le fil, l'onglet Profil et les Réglages n'existaient pas encore sur iOS : après l'onboarding, l'app s'ouvre sur un **accueil provisoire** (la Miff de la personne, ou « Pas encore de Miff »), avec un bouton de déconnexion.)

L'icône et le mot-symbole sont les **fichiers officiels** (`design/assets/logo`, validés par le PM le 2026-10-27) : l'icône est `Miff/Resources/Assets.xcassets/AppIcon.appiconset`, le mot-symbole est dessiné en vectoriel (`Miff/DesignSystem/Logo/`) à partir des tracés de `design/assets/logo` (générés par `tools/generate-logo-paths.mjs`, jamais retapés à la main). Le « G » du bouton Google est un **redessin** à remplacer par le visuel officiel des directives de marque de Google avant la fiche de l'App Store (voir « Écarts »).

**Poste Windows sans Mac** : rien ne se compile ni ne se teste en local. Tout est validé par la CI (GitHub Actions, runner `macos-26`) et, pour ce qui touche à l'iPhone (signature, App Attest, rendu réel), par TestFlight. Les passages marqués « à vérifier » sont des points que seul un vrai iPhone peut confirmer.

## Principe

Il n'y a **pas de `.xcodeproj` dans le dépôt**. Le projet est décrit dans `project.yml` et généré par [XcodeGen](https://github.com/yonaskolb/XcodeGen) (MIT) :

```sh
xcodegen generate --spec project.yml   # sur un Mac ; la CI le fait toute seule
```

## Architecture

MVVM simple, sans bibliothèque d'injection : `View` (SwiftUI) -> `ViewModel` (`ObservableObject`, `@Published`, `async/await`) -> `Services` / `Models`. Le `@Observable` d'iOS 17 n'est pas utilisé (iOS 16 minimum). `NavigationStack` pour la navigation. Les dépendances sont passées par initialiseur via `AppEnvironment`. Mode de langage Swift 5 (pas Swift 6 strict) : décision du spike, à réévaluer quand les écrans de fonctionnalités arriveront.

## Configuration Firebase (projet `miff-3d283`)

`GoogleService-Info.plist` n'est **jamais** dans le dépôt (`.gitignore`, contrôlé par le job `hygiene`).

- **CI** : le workflow `ios` (et `ios-testflight`) le recrée avant la génération du projet depuis le secret GitHub `GOOGLE_SERVICE_INFO_PLIST_B64` (base64), vérifie `PROJECT_ID = miff-3d283` et `BUNDLE_ID = com.tomessa.miff`, puis le supprime en fin de job. Une PR de Dependabot, qui ne peut pas lire les secrets, reçoit un fichier **évidemment factice** (`fake-ci-config-do-not-use`) : le projet compile, aucune capture n'est publiée.
- **Secret manquant** : le job échoue avec « Secret manquant ». Création (PowerShell) : `[Convert]::ToBase64String([IO.File]::ReadAllBytes("chemin\GoogleService-Info.plist")) | gh secret set GOOGLE_SERVICE_INFO_PLIST_B64 --repo Tomessa-Ghostrun/Miff`.
- **Poste de développement (Mac)** : `firebase apps:sdkconfig IOS 1:29899146512:ios:94e30481497dd74c659195 --project miff-3d283 > Config/GoogleService-Info.plist`, puis `xcodegen generate`. Toujours avec `--project miff-3d283` ; le projet `ghostrun-app` n'est jamais ciblé. Sans ce fichier l'app démarre quand même (Firebase n'est simplement pas configuré, le diagnostic affiche « Projet non identifié »).
- **Tests unitaires** : Firebase n'est pas configuré dans le processus de test (aucun réseau, rien d'envoyé).

## Authentification, onboarding et profil (AUTH-3, AUTH-4, ONB-5, ONB-6)

Parité avec Android (mêmes tickets `docs/tickets/authentification.md` et `onboarding.md`, mêmes décisions du PM `onboarding-decisions-pm.md`) ; le code Android de référence est dans `android/.../ui/auth`, `ui/profile`, `ui/onboarding`, `ui/splash`, `data/session/SessionManager.kt`.

- **Une seule source de vérité pour « où s'ouvre l'app »** : `Services/Session/SessionManager` (Swift pur, testé avec des doubles). La destination vient de l'état du **compte** (profil ? numéro ? Miff ?), jamais de « une connexion vient d'avoir lieu » (`resolveDestination`). `SessionObservable` la publie à l'interface ; `Views/AppRootView` ne fait que l'afficher.
- **Inscription** : e-mail et mot de passe (8 caractères au moins, aucune règle de complexité), Google, Apple. **Aucune case à cocher** : la ligne au-dessus du bouton dit que « Rejoindre » (ou « Continuer avec Apple » / « Continuer avec Google ») accepte les conditions, la politique et le partage de statistiques anonymes ; le geste vaut acceptation et rien n'est collecté avant. Une personne nouvelle qui arrive par Google ou Apple depuis l'écran de **connexion** reçoit le panneau de consentement ; le refuser supprime le compte tout juste créé (ré-authentification Google ou Apple si Firebase la réclame).
- **Connexion** : un seul message pour « adresse inconnue » et « mauvais mot de passe », avec un plancher de 800 ms sur la durée de cette réponse ; pause de confort après 5 échecs (30 s). **Mot de passe oublié** : une confirmation identique pour toute adresse, pause de 60 s par adresse ; le nouveau mot de passe se choisit sur la page web d'AUTH-W.
- **Profil** (ONB-6) : étape profil (photo facultative, prénom, nom) puis étape téléphone (pays, numéro national, E.164 enregistré, **obligatoire**). Rien n'est écrit à l'étape profil : un **brouillon local** (stockage privé de l'app, exclu des sauvegardes, effacé à la déconnexion et après confirmation) garde la saisie ; UNE écriture par **transaction** Firestore (délai de 20 s) à la fin, confirmée par le serveur avant l'écran suivant.
- **Photo** : sélecteur de photos du système (`PhotosPicker`, **aucune permission**), recadrage carré obligatoire, puis JPEG **ré-encodé depuis les pixels** (aucune métadonnée de la photo d'origine : ni position, ni date, ni appareil), 20 000 octets au plus. Testé avec une photo qui porte une position GPS.
- **Numéro** : [PhoneNumberKit](https://github.com/PhoneNumberKit/PhoneNumberKit) 5.0.13 (MIT ; le dépôt historique `marmelroy/PhoneNumberKit` n'est pas archivé mais n'a plus de version depuis la 4.3.0 de mai 2026, les versions 5.x sont publiées par l'organisation `PhoneNumberKit`), mêmes métadonnées (libphonenumber 9.0.42) et mêmes cas de test qu'Android ; seuls les genres fixe, mobile et voix sur IP sont acceptés (comme Android).
- **Carrousel** (première ouverture seulement), **écran de lancement** : voir « Carrousel et lancement » ci-dessous.
- **Rien n'est journalisé** : ni mot de passe, ni adresse e-mail, ni nom, ni numéro, ni jeton. Les jetons Google et Apple vont à Firebase Authentication et nulle part ailleurs ; leur description textuelle est volontairement masquée.

### Connexion Google

- SDK `GoogleSignIn-iOS` 10.1.0 (Apache-2.0, version exacte). La 9.x n'est pas compatible avec Firebase 13 (conflit sur `app-check`).
- L'identifiant du client OAuth vient de `GoogleService-Info.plist` (`CLIENT_ID`). Le **schéma d'URL de retour** (`REVERSED_CLIENT_ID`) doit être déclaré dans l'`Info.plist` ; comme le fichier de configuration n'est jamais dans le dépôt, la phase de compilation « Google - schéma d'URL de retour » (`ci/inject-google-url-scheme.sh`) le lit dans le fichier embarqué et l'ajoute à l'`Info.plist` **du build** (sans jamais l'afficher). Le contrôle `ci/check-binaries.sh` vérifie qu'il y est.
- **Prérequis côté PM** : le fichier de configuration actuel a été généré **avant** l'activation de Google dans Firebase Authentication ; il n'a donc peut-être ni `CLIENT_ID` ni `REVERSED_CLIENT_ID`. Le régénérer (`firebase apps:sdkconfig IOS 1:29899146512:ios:94e30481497dd74c659195 --project miff-3d283`) puis mettre à jour le secret `GOOGLE_SERVICE_INFO_PLIST_B64`. Sans cela, le bouton Google affiche le message neutre d'erreur (la CI avertit).

### Connexion Apple

- Natif (`AuthenticationServices`) : jeton à usage unique (nonce de 32 caractères tirés avec `SecRandomCopyBytes`, seule l'empreinte SHA-256 est donnée à Apple), le prénom et le nom ne sont donnés qu'à la première connexion et ne servent qu'à préremplir l'étape profil. Bouton : `ASAuthorizationAppleIDButton` officiel (libellé « Continuer avec Apple » fourni par le système, selon la langue du téléphone).
- **Prérequis côté PM** (en cours) : activer la capacité « Sign in with Apple » sur l'identifiant `com.tomessa.miff` (developer.apple.com) **et** le fournisseur Apple dans Firebase Authentication. Sans la capacité, la signature automatique de l'archive TestFlight échoue ; sans le fournisseur Firebase, le bouton Apple répond par le message neutre d'erreur.

### Carrousel et lancement (ONB-5)

- **Icône** : l'icône officielle (`design/assets/logo/ios`).
- **Carrousel** : 3 slides (balayage seulement, aucun défilement automatique), une seule phrase d'accroche, « Commencer » sur chaque slide, « J'ai déjà un compte ». Affiché **uniquement à la première ouverture sans session** ; jamais après une déconnexion. Les illustrations sont **reconstruites en vectoriel et en vrais textes** à partir des maquettes (`design/exports/onboarding-original`), comme sur Android ; seules les photos (profils, salon, fond de carte) sont des images.
- **Écran de lancement** : l'écran système (fond bleu, « M + i » blanc, sans le cœur, `UILaunchScreen`) est suivi de l'animation (`Views/Splash`) : le cœur apparaît, gonfle puis éclate (2,9 s au total, 3 s au plus, mesurées en temps réel). Avec « Réduire les animations » : logo complet immobile 0,8 s. La chronologie est une fonction pure du temps (`SplashTimeline`, testée).

## Écarts avec les maquettes et avec Android

1. **Photo de profil sans option « appareil photo »** (Android la propose) : sur iOS elle demanderait la permission de la caméra, que l'app n'a pas (aucune permission demandée). Clés `profile_photo_take` et `profile_photo_camera_unavailable` conservées pour la parité du catalogue, non utilisées.
2. **Bouton Apple** : composant système (libellé, police et forme d'Apple) ; la maquette en dessine un. La ligne de consentement de l'inscription cite aussi ce bouton (clé `ios_auth_consent_notice`, propre à iOS).
3. **Bouton Google** : police du système (Roboto n'est pas embarquée) ; le « G » est un **redessin à remplacer** par le visuel officiel avant la fiche de l'App Store.
4. **Sélecteur de photos** : celui du système (les maquettes n'en dessinent pas) ; le recadrage carré est un écran ajouté (non dessiné), dans le même style.
5. **Retour** : flèche de l'en-tête ET geste natif de balayage depuis le bord (navigation native `NavigationStack`).
6. **Cible tactile** de 44 pt (Apple) au lieu de 48 dp.
7. **Session après réinstallation** : sur iOS, la session Firebase est gardée dans le **Trousseau**, qui survit à la désinstallation, alors que les réglages de l'app (carrousel vu, etc.) disparaissent avec elle. Pour qu'une app réinstallée ne s'ouvre pas connectée sans que la personne ait revu le carrousel ni le consentement, **au premier lancement d'une installation** (repère absent des réglages de l'app) une session trouvée est **fermée** avant tout routage : la personne se reconnecte (écran de connexion). Conséquence visible : après une réinstallation, il faut se reconnecter. Recommandation de la revue, appliquée sauf veto du PM ; testée (`SessionSafetyTests`). Android n'a pas ce cas (une désinstallation efface tout).
8. **Barre d'état pendant le lancement animé** : l'animation occupe tout l'écran, barre d'état comprise.
9. **Exemple de numéro** du champ téléphone : fourni par PhoneNumberKit (exemple de mobile du pays), formaté sans l'indicatif ni le premier zéro.
10. **Réglages et retrait du consentement** : l'écran Réglages / Confidentialité d'Android (ONB-3b) n'existe pas encore sur iOS. Le consentement aux statistiques est donné par le geste d'inscription, et le retirer doit rester aussi simple que le donner (RGPD art. 7(3)). Tant que l'écran n'existe pas, **le texte de consentement iOS ne promet plus « modifiable dans les Réglages »** : il dit « tu peux le retirer à tout moment en écrivant à » l'adresse de contact (clés `ios_auth_consent_notice` et `ios_auth_panel_notice`, propres à iOS ; les clés d'Android `auth_consent_notice` et `auth_panel_notice` restent dans le catalogue pour la parité). Choix : adapter le texte plutôt que créer un écran de confidentialité minimal, qui dupliquerait le ticket Réglages (retrait immédiat, effacement des rapports, écriture du compte) hors du périmètre de ce lot. **Limite** : le retrait passe par un e-mail traité à la main ; le ticket iOS Réglages devra rétablir un retrait dans l'app, puis remettre le texte d'Android. À valider par le PM (décision légale).

## Miffs : créer, rejoindre, écran de la Miff, partage, accès perdu (MIFF-3)

Miroir iOS d'Android MIFF-1 (tickets `docs/tickets/miff.md` §8 et §16, décisions du PM `miff-questions-pm.md`, `feed-profil-reglages.md` §13, maquettes `design/exports/miff/`, `onboarding-original/` -3 et -18, `feed/` -2 et -3, fiches `design/screens/miff-*.md`). Mêmes règles métier, **mêmes textes FR/EN** (clés `miff_*`, `feed_*`, `profile_tab_*` du catalogue, reprises d'Android), **mêmes écritures** (aucune règle Firestore modifiée) :

- **Créer** : « Nouvelle Miff » (nom de 2 à 40 caractères, texte de partage au-dessus de « Créer et partager »), puis « Ta Miff « X » est prête » (code par groupes de 4, Partager, Copier). **UN lot de 5 écritures** (Miff, code, fiche du créateur avec consentement daté et versionné, index, statut initial `unknown`) dans UNE transaction, code tiré à ce moment (`SecRandomCopyBytes`, échantillonnage par rejet : aucun biais de modulo), jusqu'à 3 tirages en cas de collision.
- **Rejoindre** : saisie du code (majuscules, clavier ASCII, ni correction ni suggestions, espaces et tirets normalisés, **bouton système « Coller » `PasteButton`** : aucune alerte de collage, jamais de lecture automatique du presse-papiers, message local sans réseau pour un caractère hors alphabet, pause d'une minute après 5 échecs), vérifications dans l'ordre du ticket §5.4 (format, lecture du code, nettoyage d'un index obsolète, déjà membre par le champ `miffId`), écran de confirmation avec le texte de partage **avant** « Rejoindre et partager », **UN lot de 3 écritures**. Rien n'est écrit avant l'appui.
- **Écran de la Miff** (créateur et membre) : nom modifiable par le créateur (lot Miff + nom du code), code et partage (`ShareLink`, feuille système), proches en direct, ligne « Partager mon statut » (arrêter / reprendre à tout moment : arrêt = fiche + suppression du statut et de la photo dans le même lot ; reprise = nouveau consentement + statut initial, dans une feuille qui montre le même cadre de consentement), lieux en liste, « Cette Miff est bien remplie ! » à 15 membres (plafond doux), lecture seule hors connexion.
- **Accès perdu** : détecté en direct (écoute refusée ou Miff inexistante) et à l'ouverture (contrôle auprès du serveur) ; **une erreur réseau n'en est jamais une**, et un refus n'est retenu que si le serveur répond par ailleurs. Un seul message, nettoyage (lot « Quitter », sinon l'index seul), purge du cache local, bascule vers l'état « Pas encore de Miff ».
- **Accueil provisoire** (destination « fil », à la place de l'ancien écran provisoire) : pastille avec le nom de la Miff (non touchable avec un compte gratuit ; sélecteur avec « + Rejoindre / + Créer » pour un Premium), carte « Mes Miffs » qui ouvre l'écran de la Miff (sur Android elle est dans l'onglet Profil), état « Pas encore de Miff » avec « Créer une Miff » / « Rejoindre une Miff », bouton « Se déconnecter » (faute d'écran Réglages). L'écran « Choisis comment tu veux commencer » remplace l'ancien écran provisoire de l'onboarding.
- **Architecture** : `Models/Miff/` (Swift pur, testé), `Services/Contracts/MiffContracts.swift` (`MiffStore`, `MiffObserver`, `MiffRepository`), `Services/Miff/MiffRepository.swift` (toute la logique, derrière `MiffStore`) et `MiffDirectory` (les Miffs en mémoire pour la session ; l'UNIQUE endroit où une perte d'accès est traitée), `Services/Firebase/FirestoreMiffStore.swift` et `FirestoreMiffObserver.swift` (les adaptateurs Firestore), `ViewModels/` et `Views/Miff/`.

**Sécurité et confidentialité** (revue demandée par le ticket, critères V1, V2, T5) :
- Le code et le nom d'une Miff ne sont **jamais journalisés** (aucun `print`, aucun journal ; chaque type qui porte un nom, un code ou un profil a une `description` masquée), jamais dans un événement Analytics (`miff_created` et `miff_joined` ne portent que `is_first_miff`), jamais dans un message d'erreur (toute erreur est réduite à une catégorie : `MiffFailure`).
- **Aucun équivalent de `rememberSaveable`** : le code tapé ou affiché ne vit que dans l'état du view model (mémoire) ; aucune restauration d'état de l'interface ne le garde. Seul l'identifiant de la Miff voyage dans une destination de navigation.
- **Presse-papiers** : « Copier » met le code SEUL, **marqué « local seulement »** (pas de presse-papiers universel vers les autres appareils) avec une **expiration à 2 minutes** ; « Coller » est le bouton système (iOS 16), l'app ne lit jamais le presse-papiers.
- **Sélecteur d'applications** : les écrans qui montrent ou saisissent le code (saisie du code, « Ta Miff est prête », écran de la Miff) sont **recouverts** (fond de l'app et mot-symbole) dès que l'app n'est plus au premier plan : la vignette du sélecteur ne montre jamais le code (`hidesInAppSwitcher`, d'après `scenePhase`). **Non vérifié sur iPhone** (voir « Limites »).
- **Noms reçus du réseau nettoyés** (`MiffName.clean`) : nom de la Miff lu dans `joinCodes` ET dans `miffs`, noms et prénoms des membres, noms des lieux (caractères de contrôle, contrôles bidirectionnels, espaces de largeur nulle) ; photos de plus de 20 000 octets ignorées ; tout identifiant lu sur le réseau est vérifié (20 lettres et chiffres, ou « free ») avant de devenir un morceau de chemin.
- **Écritures transactionnelles** : toutes les écritures sont des transactions (`runTransaction`) : « pas de confirmation » veut toujours dire « rien d'écrit », jamais de file d'attente rejouée plus tard ; le succès ne s'affiche qu'après l'accusé du serveur ; un lot parti dont la réponse s'est perdue est vérifié auprès du serveur avant d'être appelé un échec.
- **Purge du cache** à la déconnexion (déjà en place, `SessionManager`) ; l'annuaire des Miffs fait partie des arrêts de la session et oublie Miffs, message et choix. **Démarrage à froid** : rien de MIFF-3 n'ouvre Firestore avant la session (le dépôt, le magasin et l'écoute ne résolvent `Firestore.firestore()` qu'à la première requête d'un écran affiché après le routage ; une purge restée en attente passe toujours avant).
- **Une sortie volontaire d'une Miff ne renouvelle PAS le code** (décision du PM du 2026-10-31) : rien dans MIFF-3 ne renouvelle le code (le nettoyage après une perte d'accès ne touche pas au code) ; MIFF-4 ne devra pas le faire non plus pour « Quitter ».
- Budget des lectures de règles : mêmes lots qu'Android (créer 5 écritures, rejoindre 3, renommer 2, arrêter 3, reprendre 2, quitter 4) ; **rien n'est ajouté** à un lot.

**Marges et zones sûres** : tous les écrans défilent dans un `ScrollView` qui respecte les zones sûres (encoche, barre d'accueil) ; seuls les FONDS passent sous les barres (`ignoresSafeArea` sur le fond uniquement) ; le clavier fait remonter le contenu (`scrollDismissesKeyboard`). Vérifiable sur les captures de la CI (`50-*` à `67-*`, dont deux avec la plus grande taille de texte) et à relire sur l'iPhone 11 Pro.

## Un compte, un seul appareil (SESS-3)

Miroir iOS d'Android SESS-2 (ticket `docs/tickets/session-appareil-unique.md`, contrat client de `backend/data-model.md`, section « Un compte, un seul appareil » ; règles SESS-1 temps 1 déployées, **aucune règle modifiée**). C'est une **mesure de cohérence, pas de sécurité** (un client modifié peut recopier l'identifiant) : un vieux téléphone resté à la maison ne doit pas continuer à dire « tout va bien » pour une personne partie avec l'autre.

- **Architecture** : `Models/Session/DeviceId.swift` (forme et génération de l'identifiant), `Models/Session/SessionWriteGuard.swift` (le garde « `deviceId` dans chaque statut et position »), `Services/Contracts/SessionContracts.swift` (contrats `DeviceSessionRemote`, `DeviceIdStore`, verdicts), `Services/Session/DeviceSession.swift` (tableau de décision, `currentDeviceId`, `clearance`), `Services/Session/SessionManager+Device.swift` (connexion, écoute, vérification sérialisée, fin volontaire), `Services/Firebase/FirestoreDeviceSessionRemote.swift` (transactions et écoute du document), `Services/Storage/DeviceIdFileStore.swift` (le fichier de l'identifiant).
- **Identifiant** : 24 octets de `SecRandomCopyBytes` encodés en base64 « adapté aux adresses » (32 caractères `A-Za-z0-9_-`, la forme exacte des règles), **tiré à chaque connexion**, jamais dérivé de l'appareil, **jamais dans un journal, Analytics ou Crashlytics** (les types qui le portent cachent leur contenu dans leur description). Gardé dans **un fichier d'Application Support exclu des sauvegardes**, protection `completeUntilFirstUserAuthentication` (lisible en arrière-plan téléphone verrouillé, pour LOC-4b). Ni Trousseau (il survit à la désinstallation : l'app se croirait encore l'appareil actif), ni `UserDefaults` (sauvegardé : un téléphone restauré hériterait de l'identifiant d'un autre).
- **Connexion** : identifiant tiré et gardé comme **candidat** (fichier `device-id.pending`), session écrite par **transaction** (deux essais avec le MÊME identifiant, 8 s), candidat **confirmé** après l'accusé, puis seulement lecture du compte et écoute. Sans accusé : écran « Réessayer » (le compte n'est pas lu, aucune écriture de statut ne peut partir), mais l'écoute et le suivi du réseau tournent déjà et reprennent la connexion au retour du réseau. La reprise **automatique** d'un candidat (lancement, retour du réseau) LIT D'ABORD le serveur : candidat ou absente = on confirme ou on écrit ; session d'un autre identifiant = remplacé (la dernière connexion réelle gagne) ; seul « Réessayer » reprend la place. Le candidat survit à un processus tué et est réutilisé par l'essai suivant : une écriture tardive d'un essai précédent (transaction expirée côté téléphone puis validée par le serveur) écrit le même identifiant et ne peut pas écraser une session plus récente. **Limite** : un candidat qui n'a jamais atteint le serveur et dont l'essai suivant n'a pas lieu est supprimé à la déconnexion.
- **Écoute** : instantanés du document ignorés s'ils viennent du cache ou d'une écriture locale encore en attente. Verdict : la mienne = confirmée ; une autre, ou disparue alors que j'avais un identifiant = **remplacée** ; aucune session ET aucun identifiant = ancienne installation, j'en écris une. Les vérifications sont **sérialisées** (une seule à la fois ; celle qui arrive pendant une autre est rejouée par une lecture du serveur), et toutes les opérations qui lisent ou écrivent la session passent par une porte à un seul passage (`AsyncGate`). Si l'écoute se termine toute seule, plus rien n'est confirmé, elle est relancée (3 fois au plus, après 15, 30 puis 60 s) et la session est relue ; **chaque retour du réseau relit la session** (une lecture). **Lectures au lancement : environ 2** (la lecture explicite AVANT de lire le compte, plus le premier instantané du serveur de l'écoute), pas 1.
- **Déconnexion forcée** (`endLocally`) : ne touche JAMAIS à la session sur le serveur ; l'appareil reste révoqué jusqu'à sa prochaine connexion par un **marqueur persistant** (`device-revoked`, posé avant l'oubli de l'identifiant et la purge), donc même un refus d'écriture tardif, ou un processus tué entre l'oubli et la déconnexion, ne peut pas réécrire une session. `release` et la suppression de session avant celle d'un compte posent aussi ce marqueur tout de suite (un compte gardé le lève en réécrivant sa session). Elle tourne dans sa propre tâche (elle n'est pas coupée par l'arrêt des écoutes). Un stockage local **illisible** est un état indéterminé : ni remplacé, ni « aucune session ». Une seule fin de session à la fois (`ending`), compatible avec `handleUidChange` : la déconnexion locale annoncée en retour est ignorée.
- **Écriture d'un statut ou d'une position** : l'identifiant vient **uniquement** de `DeviceSession.currentDeviceId` (rempli seulement quand le serveur a confirmé). `SessionWriteGuard` refuse AVANT l'envoi tout `set` / `update` d'un statut ou d'une position sans `deviceId` valide.

**Pour LOC-4b (détection et statuts)** : construire les champs de chaque écriture avec `SessionWriteGuard.stamped(_:deviceId:)` ; obtenir l'identifiant par `await device.clearance(uid:)` avant la première écriture d'une série (réveil à froid en arrière-plan : le serveur est interrogé une fois, un remplacement lance la déconnexion forcée) ; après un **refus** d'écriture, appeler `device.checkAfterRefusal(uid:)` (relit la session ; ne dit pas « remplacé » sur un simple refus de consentement). Mises à jour partielles du statut : la clé `deviceId` doit être envoyée aussi (les règles ne peuvent pas l'exiger : SF9). Si une déconnexion forcée a lieu quand l'app est fermée, le message est conservé (`session_replaced_notice_pending`, même clé qu'Android) jusqu'à l'écran de connexion.

**Pour AUTH-5 (suppression de compte, faite en AUTH-5c : la procédure supprime la session via `DeviceSession.deleteForAccountDeletion`, qui ferme l'appareil d'abord ; `deleteDeviceSessionBeforeAccountRemoval` ne sert plus qu'au refus du panneau de consentement)** : appeler `deleteDeviceSessionBeforeAccountRemoval(uid:)` ; **sans accusé de suppression (faux), ne pas supprimer le compte Auth** (abandon, puis `resumeDeviceWatch()` : la procédure est reprenable) ; en détail : arrêter d'abord l'écoute (`stopDeviceWatch()`, pour que sa propre suppression ne soit pas lue comme un remplacement), puis supprimer `users/{uid}/session/active` à l'étape 3 avec `devices`, avant `users/{uid}` (reprenable) ; les autres appareils constatent la disparition du document (instantané du serveur) et se déconnectent d'eux-mêmes. Le refus du panneau de consentement le fait déjà pour son compte tout juste créé.

### Écarts avec Android (SESS-3)

1. **Accusé manquant à la connexion** : l'iPhone **reste connecté** sur l'écran « Réessayer » (`pendingDeviceBegin`) ; Android **annule la connexion** et affiche « pas de connexion ». Raison : pour une inscription, annuler laisserait un compte créé mais inutilisable (« adresse déjà utilisée » au nouvel essai). À aligner si le PM préfère le comportement d'Android.
2. **Lancement** : l'iPhone vérifie la session **puis** lit le compte (une lecture après l'autre) ; Android les fait en parallèle. L'iPhone ne lit même pas le compte si la session est remplacée ; il ne fait **aucune** lecture de session quand le système dit « hors ligne » (pas de délai d'attente).
3. **Écoute** : l'écoute du document est ouverte tout de suite (les instantanés du cache sont ignorés) et la vérification au retour du réseau se fait tant que le serveur n'a pas confirmé ; Android vérifie puis écoute, avec des nouvelles tentatives à 15, 30 et 60 s. Pas de nouvelle tentative temporisée sur iPhone (le retour du réseau suffit).
4. **Stockage** : fichier d'Application Support (Android : fichier privé), tous deux hors sauvegardes.

**Invariants tenus (chacun a un test)** :
1. **Marqueur local « suppression en cours » écrit AVANT toute écriture**, prioritaire sur le routage du lancement (`AppDestination.accountDeletion`) : un profil déjà supprimé n'envoie jamais la personne vers « crée ton profil ». Un marqueur d'un AUTRE compte est ignoré et effacé. Plus de session au lancement : si Firebase avait CONFIRMÉ la suppression (`accountDeleted` écrit avant le nettoyage), c'est un succès (nettoyage, carrousel, bannière) ; sinon la session a été fermée dans notre dos, le marqueur reste, rien ne dit « supprimé ».
2. **Étape 0** : écoutes, suivi des lieux (régions désarmées), écritures de statut et de position arrêtés AVANT le premier document ; l'appareil est **fermé** (`DeviceSession.closeForAccountDeletion` : le marqueur « révoqué » de SESS-3 est sur le disque tout de suite), donc aucune vérification ne réécrit une session et aucun réveil par une zone n'écrit un statut ou une position pendant la suppression.
3. **Ordre** : inventaire lu sur le serveur → **session d'appareil supprimée (accusé du serveur)** → index périmés → Miffs REJOINTES (lot « Quitter », aucun changement de code) → Miffs CRÉÉES l'une après l'autre (`MiffDeletion` : retrait des membres un par un, lieux, dernier lot) → index recomptés (`maxPasses` = 3, puis annulation) → appareils → session encore → vérification finale (`memberships` vide) → **profil EN DERNIER document** → écritures en attente envoyées → **compte d'authentification EN DERNIER**.
4. **Seul « utilisateur introuvable » (code 17011) veut dire « déjà supprimé »** (`AuthFailure.accountGone`). Jeton expiré ou révoqué (17021, 17017), « personne de connecté », session fermée = `sessionExpired` : jamais un succès, la personne se reconnecte, la suppression reprend. Une étape refusée interroge `checkSession` : compte disparu = succès voulu.
5. **Jamais de compte ni de profil supprimé avec une Miff créée derrière** : un échec durable (trois essais) laisse tout tel quel avec le contact ; des Miffs qui continuent d'apparaître annulent la suppression (`miffsRemain`, message calme).
6. **Reprenable après n'importe quelle coupure** (app tuée, réseau coupé, réponse perdue) : chaque étape est décidée d'après le serveur, jamais d'un compteur local ; testé en rejouant la procédure après un échec à chaque étape.
7. **Purge locale** (`eraseAfterAccountDeletion`) : drapeau de purge posé AVANT, cache Firestore purgé, réglages du compte (`AccountLocalData`), carnets du profil, consentement en attente, collecte Analytics et rapports de plantage effacés + identifiant d'installation d'Analytics réinitialisé, session locale fermée, régions désarmées (par l'arrêt du suivi), notifications locales retirées ; marqueur EN DERNIER. **Aucun élément du Trousseau propre à l'app** (la session Firebase et celle de Google Sign-In partent avec la déconnexion). Tout nouveau stockage lié à un compte doit être ajouté à `AccountLocalData` ou au `SessionTeardown`.
8. **Aucune donnée personnelle** dans un journal, un événement ou un message : types qui portent un nom ou un identifiant à description masquée, aucun `print`/`Logger`, aucun appel réseau hors Firebase (test sur les sources : `AccountDeletionSourcesTests`).

**Ré-authentification** (écran C) : mot de passe, Google ou Apple, selon les méthodes réellement liées au compte (`linkedProviders`). Mauvais mot de passe : « Ce mot de passe ne correspond pas. » sans compteur punitif ; autre compte Google ou Apple que celui de la session : « Ce n'est pas le compte avec lequel tu es connecté(e)… » ; fenêtre fermée : aucun message ; pas de réseau : message calme, rien n'est lancé ; « Mot de passe oublié ? » ouvre l'écran d'AUTH-4 dans une feuille (la suppression n'a pas commencé). Le mot de passe est un paramètre, jamais un champ de l'état, et le champ est vidé quand l'écran part. Si Firebase réclame une connexion plus récente à la toute fin : « Dernière vérification avant de terminer » (même écran).

**Apple (règle 5.1.1(v) et « Sign in with Apple »)** : un compte lié à Apple se ré-authentifie par la feuille officielle (bouton système) SEULE ; son code d'autorisation sert tout de suite à `Auth.revokeToken(withAuthorizationCode:)` (SDK Firebase 13.1.1, **sans serveur à nous, sans Cloud Function, sans clé dans l'app ni dans le dépôt**). La clé `.p8` est saisie par le PM dans la console Firebase (fournisseur Apple) : **tant qu'elle ne l'est pas, la révocation échoue**, la suppression continue (décision Q8a) et l'écran de fin donne les trois étapes pour retirer l'autorisation à la main. L'interface est isolée (`AppleTokenRevoker`), testée avec un double ; le comportement réel ne se constate que sur l'iPhone (critères SI1 et SI2 de la recette). La **soumission à l'App Store reste bloquée** tant que la révocation n'est pas prouvée sur l'iPhone.

**« Compte supprimé depuis un autre téléphone »** (miroir de la PR Android #100) : `SessionJudge.judge(local:remote:)` rend `mine`, `writeNew`, `replaced` (un autre téléphone a pris la place) ou `sessionGone` (cet appareil avait un identifiant mais le DOCUMENT de session a disparu). `DeviceSession` garde la raison (`device-gone`, avec le marqueur « révoqué », persistante) ; `SessionManager.endBecauseReplaced` choisit la note : `auth_session_replaced_notice` ou la note prudente `auth_session_gone_notice`. La déconnexion locale est la même, ne touche jamais à la session sur le serveur. Les tests de SESS-3 sont inchangés, sauf un : le cas « le document disparaît » attend maintenant `sessionGone` (comportement voulu).

### Limites connues et à vérifier sur l'iPhone (AUTH-5c)

- **Écart avec Android (PR #116)** : Android n'a la roue que sur « Choisis comment tu veux commencer » (son « Pas encore de Miff » est dans la coquille à onglets, donc avec le Profil). Sur iPhone la coquille MASQUE la barre sans Miff (décision Q13), il n'y a donc pas de Profil : la même roue est posée sur « Pas encore de Miff », sinon un compte qui vient de quitter sa dernière Miff n'aurait aucun chemin vers la suppression.
- **Pas d'entrée vers les Réglages sur « On n'a pas pu lire ton compte »** : l'état du compte y est inconnu (réseau absent au lancement) ; la personne y a « Réessayer » et « Se déconnecter », et retrouve l'entrée dès que son compte est lu. Un compte sans Miff qui n'arrive jamais à se connecter au serveur ne peut de toute façon pas se supprimer (la suppression a besoin du serveur).
- **Marqueur local impossible à écrire** (disque plein, stockage refusé) : la suppression REFUSE de démarrer (message calme, rien n'a été touché), car sans lui une app tuée en route ne pourrait pas reprendre.
- **Fenêtre de coupure (quelques millisecondes, même limite qu'Android)** : si l'app est tuée entre la réponse de Firebase (compte supprimé) et l'écriture du drapeau « compte supprimé » dans le marqueur, le relancement ne trouve plus de session et un marqueur « pas confirmé » : l'app le traite comme une session fermée et propose de se reconnecter, ce qui échoue puisque le compte n'existe plus ; le marqueur s'efface à la connexion ou à l'inscription d'un autre compte. Les données du serveur sont déjà toutes supprimées à ce stade ; le cache Firestore est purgé au lancement (la purge est enregistrée avant le compte), seuls les petits drapeaux locaux du compte ne sont pas refaits. À surveiller à la recette plutôt qu'à corriger : risque très faible.
- **Révocation Apple** : faite à la ré-authentification, AVANT les suppressions de données (le code d'autorisation n'est jamais gardé) ; si la suppression est ensuite annulée (Miffs qui apparaissent), le lien « Se connecter avec Apple » est déjà retiré du compte Apple, et la connexion Apple suivante le recrée sans conséquence. Une révocation qui a échoué est retentée avec un code neuf à la « Dernière vérification ».

- **Rien n'est compilé ni exécuté en local** (poste Windows) : la CI fait foi ; l'alerte du système, la feuille de partage, la feuille Apple, VoiceOver, la plus grande taille de texte, `isIdleTimerDisabled` et le comportement réel d'Apple après une révocation ne se constatent que sur l'iPhone (`docs/qa/checklists/suppression-compte-ios-recette-pm.md`).
- **`Auth.revokeToken(withAuthorizationCode:)`** : l'API est celle du SDK 13.1.1 ; l'erreur d'Apple n'est pas lue (tout échec = « révocation échouée »). Aucune distinction « console non configurée » / « code expiré » possible côté app : l'écran de fin traite tous les échecs de la même façon.
- **Fenêtre de « connexion récente » de Firebase** : non documentée, non mesurée ici (SQ3) ; la « Dernière vérification » gère le cas.
- **Le code d'autorisation d'Apple vit quelques minutes** : la révocation est faite juste après la ré-authentification, avant les suppressions de données. Si la procédure échoue ensuite, le compte Miff existe encore mais Apple le considère comme « jamais autorisé » : au prochain « Continuer avec Apple », le même compte est retrouvé **à vérifier sur l'iPhone** (SI2, second cas).
- **Les copies de la personne dans le cache hors ligne des téléphones des autres membres** et `entitlements/{uid}` ne sont pas supprimables depuis le téléphone (risques R6 et R9 du ticket, purge manuelle mensuelle du PM pour `entitlements`).
- **Les rapports déjà envoyés à Analytics et Crashlytics** suivent les durées de la politique ; seul l'identifiant d'installation d'Analytics est réinitialisé (l'effet de `resetAnalyticsData` sur d'autres services n'a pas été testé).
- **Le marqueur** est un fichier d'Application Support (protection « jusqu'à la première authentification », exclu des sauvegardes) : s'il ne peut pas être écrit, la suppression tourne quand même, sans reprise automatique si l'app est tuée.

## Lieux de confiance : formulaire, adresses, carte, liste, détail, modification, suppression (LOC-3)

Miroir iOS d'Android LOC-1 (PR #56, fusionnée) : tickets `docs/tickets/lieux-de-confiance.md` (v3 et décisions du PM du 2026-11-01), fiches `design/screens/lieux/`, maquettes `design/exports/lieux/` (7 du PM) et `design/exports/lieux/claude/` (01 à 07, 14 à 17, 19, 20). ### Limites connues (LOC-3)

- **Rien n'est compilé ni testé en local** (poste Windows) : la CI fait foi ; le rendu réel (carte, feuilles, clavier qui masque la liste de suggestions, VoiceOver, texte agrandi, « Voir sur la carte ») **n'est vérifiable que sur l'iPhone** (`docs/qa/checklists/loc-3-ios-recette-pm.md`). Les tests de logique ont aussi été exécutés sous Linux (branche jetable, jamais fusionnée) : aucun échec du fait des lieux.
- **Formule inconnue** (revue I1) : l'annuaire sait maintenant si l'abonnement a été **lu auprès du serveur** (`premiumKnown`, faux après une lecture échouée ou une réponse du cache). La liste n'affirme rien de la formule gratuite dans ce cas (ni compteur « 2 lieux sur 2 », ni pastille Miff+), et « Ajouter un lieu » ouvre **toujours le formulaire**, qui relit l'abonnement et les lieux auprès du serveur et ne propose l'offre que si la limite est vraiment atteinte (un compte Miff+ n'est jamais renvoyé vers l'offre).
- **Rayon hérité** : un lieu dont le rayon n'est pas un pas permis (les règles acceptent 50 à 2 000 m) est ramené au pas le plus proche (50 à 800) à l'ouverture de la modification ; le bouton reste grisé tant que rien d'autre n'a changé.
- **Texte très grand** : aux tailles d'accessibilité, le pied du formulaire défile avec le formulaire au lieu d'être fixé en bas ; la carte garde sa hauteur, le texte qui la remplace peut grandir.
- **Document de lieu malformé** : il n'est pas montré (comme Android) ; le détail d'un tel lieu dit « Ce lieu n'existe plus » faute de pouvoir distinguer : non traité (il faudrait remonter les documents écartés).
- **Compteur « N lieux sur 2 »** : compte les lieux de la Miff affichée. **Limite gratuite avec plusieurs Miffs** (compte dont Miff+ a pris fin) : le client compte les lieux distincts de la personne (2 au plus), les règles comptent par emplacement et par Miff ; le client est plus strict, pas plus lâche.
- **Résultats trop grossiers** (une saisie comme « Paris » donne une ville) : comme Android (point ouvert m4), rien n'est filtré en v1.

### Choix du cache persistant du SDK (même décision que l'Update et « Localiser »)
La photo est lue avec `source: .server` : jamais une vieille copie du cache pour la photo d'aujourd'hui, et hors ligne la lecture échoue vite (le Feed ne montre alors rien de plus). **Limite connue et assumée** (`backend/data-model.md`, point 27) : le SDK Firestore peut garder dans son cache **persistant** le document qu'il vient de lire, octets compris, jusqu'à la purge du cache (déconnexion, perte d'accès à une Miff). **Notre code, lui, n'écrit jamais la photo** : la copie qu'il garde est en mémoire (`PhotoCache`), vidée à la déconnexion ; aucun fichier, aucune photothèque, aucun presse-papiers. Passer le cache du SDK en mémoire seule casserait le Feed hors ligne (statuts) : pas retenu.

## Suivi des lieux : arrivées, départs, dernière position (LOC-4b, miroir d'Android LOC-2b)

Ticket `docs/tickets/lieux-de-confiance.md` (v3 : §6.4 à §6.9, §7, §8, §9 à §11, §13 ; critères POS1 à POS8, DET1 à DET4, STA1 à STA9, VIE1 à VIE4, HOR1, IOS1 à IOS4), décisions du PM du 2026-11-01 et du 2026-11-06, règles **déployées le 2026-11-06** (position, session temps 1, R-LIEU-1 ; **aucune règle modifiée**), implémentation Android de référence (`data/tracking/`, `domain/tracking/`). Recette du PM, sur l'iPhone : `docs/qa/checklists/loc-4b-ios-recette-pm.md` (TestFlight, à pied). Ce que fait réellement l'app, pour la fiche et la revue d'Apple : `docs/release/ios-loc-4b-comportement-reel.md`.

- **Condition de tout** : la personne est connectée, a donné **« Toujours » + la position exacte** (service de localisation de l'iPhone allumé) ET partage avec une Miff sous le **consentement version 3**. Chaque entrée du moteur revérifie les trois ; un retrait est constaté au réveil suivant et tout s'arrête (zones retirées, position et état effacés). Tant que ce n'est pas le cas (« Plus tard » quand le blocage est relâché, autorisation retirée, ancien texte non renouvelé), **aucune position n'est lue, aucune zone n'est surveillée, rien n'est écrit** sauf `locationAccess` (une fois par changement) : c'est le « Feed sans localisation » du ticket (`TrackingEngineTests`, `TrackingEngineSessionTests`).
- **Où** : `Models/Tracking/` (logique pure : `ZoneSelection`, `PresenceMachine`, `StatusColor`, `TrackingLimits`, `TrackingWrites`, `LocationAccessRule`, journal, copie locale), `Services/Tracking/` (`TrackingEngine` et ses trois extensions, `TrackingRuntime`, `LocationTracking` (la logique du pont, testée avec un faux gestionnaire), `LocationManaging` (le protocole, sans CoreLocation), `SystemLocationManager` : **le seul fichier qui demande une position et surveille des régions**, `TrackingLocalFileStore`, `FileDetectionJournal`, `SystemTrackingEnvironment`, `FirestoreTrackingStore`), `App/TrackingServices.swift` (câblage), `Views/TrackingLifecycle.swift` (premier plan / arrière-plan). Moteur et pont testés avec des doubles (`MiffTests/Support/TrackingDoubles.swift` : faux gestionnaire de localisation `FakeLocationManager`, faux destinataire `RecordingSink`) : `TrackingEngine*Tests`, `TrackingEngineRobustnessTests` (relectures, ordre, doublons, abandon) et `LocationTrackingTests` (le pont : doublons, nouvelle autorisation, position abandonnée, `didDetermineState`).
- **Démarrage** : le gestionnaire de localisation et son délégué sont créés **tout de suite** au lancement de l'app (`AppEnvironment.init`), y compris quand le système relance l'app terminée en arrière-plan : c'est la condition pour que l'événement en attente soit livré. Il ne lit rien et n'arme rien tant que le moteur n'a pas vérifié les trois conditions.
- **Quand la position est lue** (`requestLocation`, précision de 100 m) : à l'ouverture (`scenePhase` actif), au passage en arrière-plan, sur un **changement de position significatif** (`startMonitoringSignificantLocationChanges`, la position fournie par le système est celle de l'occasion) et à chaque **entrée dans une zone**. **Les rappels d'entrée / de sortie de région ne lisent aucune position** (`didEnterRegion`, `didExitRegion`, `didDetermineState` ne prennent que l'identifiant de la région : test statique `testTheRegionCallbacksReadNoPosition`). Aucune position de plus de 10 min n'est utilisée ; le repli sur la dernière position du système n'est accepté que s'il a moins de 2 min. **Aucune mise à jour continue**, donc aucun mode d'arrière-plan « location » (voir plus bas).
- **Les 20 zones** : `CLCircularRegion`, 20 au plus, choisies comme sur Android : d'abord celles où la personne **se trouve**, puis les plus proches par le **bord**, liste **locale**, aucune requête serveur au recalcul. Une zone est nommée par sa **clé** (identifiant + géométrie + type), jamais par l'identifiant seul ; un lieu dans plusieurs Miffs est **une seule zone**. **Une ouverture ordinaire ne réenregistre rien** : seules les zones qui manquent au système sont enregistrées (le système fait foi : ce qu'il détient et que la liste ne veut plus est retiré), et `requestState` n'est demandé que pour les **zones nouvelles** et là où la **position contredit ce que l'app croit** (dedans alors qu'on se croyait dehors, ou l'inverse) : **dedans = une arrivée (DET3), dehors = rien n'est inventé**. Un échec de la surveillance (`monitoringDidFail`) ou un changement de la liste fait tout réenregistrer (`reregister`), au plus une fois toutes les 5 minutes pour l'échec. Le pont ne transmet un `didDetermineState` **que pour une zone dont l'état a été demandé** : le « dehors » que le système rend après une sortie n'est donc jamais pris pour une sortie manquée.
- **Une sortie manquée** (app fermée de force, téléphone éteint) : si, à l'armement, le système dit « dehors » alors que la copie locale disait « dedans », le statut devient **`unknown`** (jamais un `out` inventé : l'heure de la sortie est inconnue), exactement comme le redémarrage d'Android.
- **Relance par le système** : fenêtre d'une dizaine de secondes. Chaque travail demande du temps (`beginBackgroundTask`) et se borne à 25 s ; le statut en attente est écrit **sur le disque avant l'envoi** (copie locale, fichier privé exclu des sauvegardes, protection « jusqu'à la première authentification » : lisible téléphone verrouillé) : si le temps manque, rien n'est perdu, l'envoi reprend au réveil suivant.
- **Écritures** (`TrackingWrites`, mêmes que celles d'Android) : **statut par Miff** = un `update` des seuls champs qui changent (`presence`, `placeId`, `presenceAt` = **heure réelle de l'événement** plafonnée à l'horloge du téléphone, `lastUpdateAt` seulement à une arrivée en zone de confiance, `batteryPct`, `locationAccess`, `escalationDueAt` nul, `updatedAt` du serveur) ; `updateText` et `hasPhoto` ne sont jamais touchés ; **la zone de confiance l'emporte** sur une zone de danger ; **dernière position** = `positions/{moi}` `{lat, lng}` à **5 décimales** + `measuredAt` (heure de la mesure), **seule**, sans historique, pour les seules Miffs sous le consentement v3. **Un document par transaction**, une écriture indépendante par Miff, les Miffs servies à tour de rôle. **`deviceId` dans CHAQUE écriture** (`SessionWriteGuard.stamped`, `DeviceSession.clearance` avant la première écriture d'un passage, `checkAfterRefusal` après un refus ; un téléphone remplacé n'écrit plus rien et le moteur s'arrête).
- **Garde-fou et disjoncteurs** (mêmes valeurs qu'Android, `TrackingLimits`) : position au plus toutes les **15 min**, sauf déplacement d'au moins **250 m**, jamais deux fois en moins de **2 min** ; **60 statuts** et **150 positions** par jour et par téléphone (jour du téléphone). Au-delà, le **dernier** état reste en attente et part après minuit s'il est encore récent. **Coût Spark** : usage normal estimé 6 à 10 statuts + 20 à 60 positions par jour et par Miff ; le pire cas est borné à 210 écritures par jour et par téléphone ; signal de bascule : écritures du jour > 12 000 de façon répétée, ou un testeur qui atteint un disjoncteur un jour normal (`docs/dev/surveillance-quotas.md`).
- **Hors connexion** : l'état le plus récent est gardé avec son heure réelle ; il part dès que le moteur retrouve le réseau **tant que le processus tourne** ; passé 24 h, il n'est **pas** abandonné en silence : il est remplacé par **`unknown` à l'heure de l'envoi** (jamais un état périmé, jamais de boucle). **Limite d'iOS (écart avec Android)** : une app suspendue ou terminée **ne peut pas être réveillée par le retour du réseau** ; ce qui attend part alors au réveil suivant (zone, déplacement significatif, ouverture) avec son heure réelle.
- **Nettoyage** : déconnexion, session remplacée (`SessionTeardown`, borné à 5 s) et, plus tard, suppression de compte (AUTH-5 appellera `stopEverything`) : zones et signalements retirés, copie locale et journal effacés, arrêt **collant** pour la session qui s'est terminée (`GenerationCounter`, copie thread-safe de `SessionManager.generation`). Partage arrêté, Miff quittée / retirée / supprimée, consentement renouvelé, lieu créé / modifié / supprimé : le moteur relit les Miffs et les lieux (`MiffRepositoryRules.onSharingChanged`, `FirestoreConsentRenewals.onRenewed`, `ChangeNotifyingPlaceRepository`). La relecture normale a lieu au plus toutes les heures (1 + 2N lectures). **Un changement de partage ou de lieu force aussi la relecture des lieux** (`refresh(.sharingChanged)` et `.rearm`, sans attendre l'heure) : ajouter, déplacer, agrandir ou supprimer un lieu est donc pris en compte tout de suite (étape A de la recette). Pas de boucle possible (une relecture ne déclenche pas de notification de changement). **Coût** : pour chaque enregistrement d'un lieu ou changement de partage par le créateur, 1 lecture de la liste des Miffs puis 2 lectures par Miff et ses lieux, soit **10 à 30 lectures** pour un compte à quelques Miffs et lieux (marge très large du quota gratuit).
- **Ordre et doublons** : les événements du système sont traités **strictement dans l'ordre où ils arrivent** (`TrackingRuntime` enchaîne chaque travail derrière le précédent) ; une deuxième arrivée dans une zone où la copie locale se croit déjà ne réécrit rien ; les deux « premier plan » d'un démarrage à froid n'en font qu'un (moins de 3 s d'écart). Le changement de position significatif est démarré **une fois par processus**, sans être redemandé à chaque ouverture, mais **redémarré** si l'app a été relancée par le système (`movement.start()` à la première ouverture ou au premier réveil d'un processus).
- **Région tout juste créée** : juste après `startMonitoring`, la liste `monitoredRegions` du système peut ne pas contenir encore la région. `SystemLocationManager` garde donc les régions qu'il vient de créer (`RegionRegistry`, par clé de zone, au plus 60 s ou jusqu'à ce que le système les montre) : elles servent à la demande d'état (`requestState`, sinon le cas « déjà dedans » à l'armement serait perdu en silence), comptent comme surveillées (pas de double enregistrement) et sont retirées par `unwatch` / désarmement même si la liste du système ne les montre pas encore. Le faux gestionnaire des tests reproduit ce cas défavorable (`listLagsBehindWatch`). **Seul l'essai sur iPhone prouve le comportement réel** (recette partie A : « si rien ne se passe sur un lieu neuf »).
- **Relance par une sortie de zone** : un processus relancé par un simple `exit` de région redemande les changements de position significatifs dès cet événement (`resumeMovementIfNeeded`), sans attendre une passe de rafraîchissement.
- **Position d'un changement significatif sans attente** : une position qui arrive alors que personne ne l'attend (la demande avait été abandonnée) va **au moteur** (`significantMove`) et n'est ni avalée ni perdue.
- **Journal de détection** (VIE2) : `FileDetectionJournal`, **compilé en Debug et Internal seulement** (`#if DEBUG || INTERNAL`) ; le build de publication reçoit `NoDetectionJournal` et la CI cherche le marqueur `DETECTIONJOURNAL` dans l'exécutable (`ci/check-binaries.sh`, témoin positif en Debug et Internal). Une liste fermée de types (`JournalKind`), l'identifiant d'un lieu (vérifié : lettres et chiffres, jamais une clé de zone), l'heure, la batterie ; **aucune coordonnée, adresse, nom**. 400 lignes au plus, fichier privé exclu des sauvegardes, effacé à la déconnexion. **Lecture sur l'iPhone, sans Mac** : build Internal, appui long de 1,5 s en haut à gauche de l'écran, carte « Journal de détection » du diagnostic (actualiser, effacer). Il note aussi si l'Actualisation en arrière-plan est coupée ou si le mode économie d'énergie est actif à l'ouverture.
- **Aucun mode d'arrière-plan** (`UIBackgroundModes` absent, IOS1) : la surveillance de régions et le changement de position significatif relancent l'app terminée sans le mode « location », réservé aux mises à jour **continues** que Miff ne fait pas (guideline 2.5.4). Justification pour Apple : `docs/release/ios-loc-4b-comportement-reel.md`. **À rouvrir seulement si la recette sur iPhone démontre une relance manquée à cause de son absence.**

### Écarts avec Android (LOC-4b)

1. **Pas de réveil au retour du réseau, pas de réarmement au redémarrage** : iOS ne fournit ni l'un ni l'autre à une app terminée. En contrepartie le système **garde les régions** après un redémarrage du téléphone et une mise à jour de l'app (à constater sur l'iPhone).
2. **L'état « dedans / dehors » est demandé au système** (`requestState`) à chaque armement ; Android compte sur le déclencheur initial `ENTER` et sur une position récente. Une sortie manquée devient `unknown` dans les deux cas.
3. **Heure d'un événement de zone** = l'heure où il arrive à l'app (comme Android), jamais lue dans une position.
4. **Les zones sont des régions du système** : iOS applique sa propre marge (environ 200 m et 20 s, guide Apple) ; un rayon sous 100 m est peu fiable (note déjà dite dans le formulaire).
5. **Encarts « En attente de ton accord » (maquette 23)** : **non construits** (ni Feed ni Réglages sur iOS ; l'écran de la Miff n'a pas d'encart). Le re-consentement est redemandé à chaque lancement (LOC-4a) et, tant qu'il n'est pas donné, le moteur ne fait rien pour cette Miff. À faire avec le Feed iOS.
6. **Aide « Si les détections tardent » (ColorOS)** : sans objet sur iPhone ; la recette note à la place l'Actualisation en arrière-plan, le mode économie d'énergie et l'app balayée.

### Limites connues et à vérifier sur l'iPhone (LOC-4b)

SwiftLint **refuse** tout autre littéral dans `Text`, `Button`, `Toggle`, `Label`, `TextField`, `SecureField`, `Section`, `.navigationTitle` et `.accessibilityLabel`, ainsi que toute couleur hexadécimale hors du design system. La CI contient un **auto-test** de ces règles (un fichier d'essai fautif doit être signalé).
- **Mêmes clés qu'Android** (contrat `docs/contracts/i18n-keys.md`, contrôle `scripts/check-i18n-parity.mjs` du job `hygiene` : 83 clés communes, vert). Le catalogue a été produit à partir des textes Android puis adapté pour iOS (unités `pt`, texte App Check, version/build).
- **Clé héritée d'Android** : `diag_build_android` affiche ici « iOS 26.5 (iPhone) ». Le nom de la clé est trompeur côté iOS ; la renommer en `diag_build_os` demande une PR sur les deux plateformes (non fait ici : `android/` n'est pas touché).
- `InfoPlist.xcstrings` : vide (aucune permission, donc aucun texte de permission).
- Tests : chaque clé a un texte français et anglais, mêmes valeurs insérées dans les deux langues, clés conformes au contrat, pluriels (`LocalizationTests`).
- Pour ajouter une langue : ajouter ses textes dans `Localizable.xcstrings` pour toutes les clés, puis son code dans `CFBundleLocalizations` (`project.yml`).
- Droite-à-gauche : mise en page avec `leading`/`trailing` (jamais gauche/droite) ; la capture CI force la direction droite-à-gauche et la mise en page se retourne. Ni Baloo Thambi 2 ni Hanken Grotesk n'ont de glyphes arabes : le système utilise sa police de repli.
- Pseudo-langue « double longueur » de la CI (`-NSDoubleLocalizedStrings YES`) : les textes sont doublés sans rien couper. Limite de l'outil : sur les textes à valeurs insérées (`%1$@`), le doublage du système fait afficher « 1$@ » dans la première moitié ; c'est un artefact de l'outil de test, pas des vraies traductions.

## Écran de diagnostic (Debug et Internal uniquement)

Même contenu et mêmes résultats que sur Android. Il ne fait **aucune écriture**.

1. **Version installée** : version, build, configuration, appareil, projet Firebase (avertissement si ce n'est pas `miff-3d283`), langue, sens du texte.
2. **Test 1** : lecture d'une Miff sans être connecté ; attendu : refus = « Règles actives : OK ». Si la lecture réussit : avertissement clair (règles ouvertes). La CI le lance au simulateur contre le vrai Firestore (une lecture, sans compte) : capture `10-fr-test1`.
3. **Test 2** : e-mail et mot de passe du compte de test (créé à la main dans la console Firebase ; jamais conservés ni écrits dans le code), lecture de `users/{uid}` et `entitlements/{uid}`, puis déconnexion. « Pas encore de profil » et « Offre : Classic » sont des résultats normaux. **Non exécuté par la CI** (pas de compte de test dans la CI).
4. **App Check** : indique si un jeton est obtenu (la valeur n'est jamais lue ni affichée).
5. **Analytics et rapports de plantage** : deux interrupteurs éteints par défaut, un événement de test, un bouton qui tente d'envoyer une position (doit être refusé), un bouton de plantage de test (actif seulement si les rapports sont activés).
6. **Galerie de tokens** : couleurs (nom de code et valeur), styles de texte, arrondis, ombres, dégradés.
7. **Langue** : phrase longue, texte court, pluriel.

Options de lancement réservées à la CI (`xcrun simctl launch ... -MiffForceRTL YES`, `-MiffShowHome YES`, `-MiffScrollTo gallery`, `-MiffAutoTest1 YES`) : `Diagnostic/DiagnosticLaunchOptions.swift`. Elles ne fonctionnent qu'en configuration **Debug** ; dans `Internal` (TestFlight) et `Release` elles sont inertes (aucun argument de lancement ne peut changer le comportement d'un build distribué).

**Accessibilité** : le résultat d'un test (apparu après un appui) est annoncé par VoiceOver (`UIAccessibility.post(.announcement)`), les lignes d'interrupteur sont une seule cible de 44 pt. **Non vérifié avec VoiceOver sur un iPhone.**

**Sécurité du diagnostic** : au démarrage, Firebase n'est configuré **que si** le `GoogleService-Info.plist` embarqué vise `miff-3d283` (sinon l'app ne parle à aucun projet : le diagnostic affiche « Projet non identifié »). Le mot de passe du test 2 n'est vidé qu'une fois la saisie validée localement (une adresse mal tapée ne force pas à retaper le mot de passe).

## CI

- `.github/workflows/ios.yml` : sur les PR qui touchent `ios/**` (**sauf** les fichiers `.md` et `ios/third_party/**`) ou les fichiers de thème Android (`android/.../ui/theme/**`, comparés par `ColorTokensTests`) : XcodeGen, résolution des paquets (cache), SwiftLint (et auto-test de ses règles), compilation et tests sur simulateur **sans signature** (un test ignoré fait échouer le job), contrôles du binaire Debug (avec témoin positif : le diagnostic et le fournisseur de débogage **doivent** y être trouvés). Les contrôles **lourds**, seulement si `Views`, `Diagnostic`, `Resources`, `DesignSystem`, `Localization`, `App`, `project.yml`, `Config`, `ci` ou le workflow changent : compilation **Release** (aucune trace du diagnostic), compilation **Internal** pour appareil (diagnostic présent, **pas** de fournisseur de débogage, Info.plist cohérent), captures d'écran (artefact `ios-screenshots-<n>`). Durées dans le résumé du job, délai maximal 30 min (relevé le 2026-10-30 : 15 min ne suffisaient plus sur les runners du dépôt public). Les contrôles s'exécutent tous même si l'un échoue ; l'étape « Verdict » fait échouer le job à la fin.
- `.github/workflows/ios-testflight.yml` : **manuel** : archive (clé d'API App Store Connect) et envoi à TestFlight. Recrée aussi `GoogleService-Info.plist` depuis le secret, applique `Package.resolved` (`-onlyUsePackageVersionsFromResolvedFile`) et le supprime en fin de job. Après l'archive : contrôle bloquant de l'identité, **puis du contenu** (Info.plist, projet Firebase embarqué, diagnostic présent, pas de fournisseur de débogage, entitlement App Attest quand il est lisible). **Jamais exécuté** (voir risques ci-dessus).
- **Symboles de plantage (Crashlytics)** : le script de phase de compilation (`ci/crashlytics-upload-symbols.sh`) **ne fait rien** en CI ou quand la clé App Store Connect est dans l'environnement : il lancerait du code tiers dans un processus qui peut lire la clé `.p8` (mode `signed`). L'envoi des dSYM se fait dans une **étape séparée sans secret** d'`ios-testflight` (la clé y est supprimée avant), jamais bloquante. **Non testé** (workflow jamais exécuté).
- Captures produites (simulateur iPhone, build Debug) : français, anglais, langue non prise en charge (doit afficher l'anglais), pseudo-langue « double longueur », droite-à-gauche (mise en page forcée), écran d'accueil, galerie, confidentialité, mode sombre du système, très grande taille de texte, et le résultat du test 1.
- **Paquets Swift** : `Package.resolved` est versionné (`ios/Package.resolved`) et copié dans le projet généré à chaque exécution. Si `project.yml` change de version sans mise à jour du fichier, le job échoue et fournit le bon fichier en artefact (`ios-resolved-<n>`). Dependabot (`swift`, dossier `/ios`) est déclaré mais **peut ne rien détecter** (projet Xcode non versionné) : voir `.github/dependabot.yml` (laissé tel quel volontairement ; à revoir si aucune PR n'arrive).
- **Données locales** : cache Firestore iOS (persistance hors ligne), sauvegardes de l'appareil : **à décider avec le contrat de purge** (DUR-3). Rien n'est purgé ni exclu des sauvegardes dans ce socle.
- Durées mesurées : voir `CHANGELOG.md` ; `docs/dev/ios-spike.md` explique le quota de minutes macOS.

## Règles

- Aucun secret dans le dépôt : clé `.p8`, configuration Firebase, jeton App Check de débogage vivent dans les secrets GitHub ou hors du dépôt (`.gitignore`, job `hygiene`).
- Aucune permission, aucune exception ATS, iPhone uniquement (`TARGETED_DEVICE_FAMILY` posé au niveau de la cible).
- Aucune API plus récente qu'iOS 16 sans garde de disponibilité (les simulateurs de la CI sont tous en iOS 26 : le compilateur détecte les API absentes, pas les différences de comportement). Aucune API plus récente n'est utilisée dans ce socle (`NavigationStack`, `ViewThatFits`, `scrollDismissesKeyboard` sont iOS 16).
